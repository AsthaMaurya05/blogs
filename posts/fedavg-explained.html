MY NOTES ON FEDERATED LEARNING, WRITTEN OUT PROPERLY

1 million phones want to train one model together. None of them want to hand over their data. Here's the algorithm that lets both things be true.

I read McMahan et al.'s "Communication-Efficient Learning of Deep Networks from Decentralized Data" (AISTATS 2017) — the paper that introduced Federated Averaging, or FedAvg — and then reproduced it from scratch in PyTorch on MNIST. This is that, cleaned up: what federated learning actually is, why FedAvg works, and what happened when I tried to break it on purpose with non-IID data.

01 · The Problem, Before Any Algorithm

Your keyboard app has great training data. It also can't have it.

Imagine a keyboard app installed on a million phones. Every phone has exactly the kind of data that would make its next-word prediction better: the words people actually type, in the order they actually type them.

The obvious way to use this data is the traditional machine learning way: collect it all on a central server, then train there.

Why that doesn't work here Nobody wants their phone uploading what they type. That includes passwords, private messages, search terms — the exact kind of data that makes the model good is the exact kind of data people don't want leaving their device.

Federated Learning flips the usual setup around. Instead of bringing the data to the model, it brings the model to the data. A phone downloads the current global model, trains it locally on whatever it has, and sends back only the updated model — never the raw data.

This is a direct application of a "data minimization" principle: only ever collect the minimum needed to improve the model, and never more. Some trust in the server is still required — but the attack surface shrinks from "the device and the cloud" down to just "the device."

02 · The Federated Learning Setup

Server, clients, and one round of communication

The paper's vocabulary is worth learning precisely, because it comes up constantly: a server coordinates training, clients are the devices, each client holds a local dataset that never leaves it, and everyone shares a global model.

One round, top to bottom:

  1. Server sends the current global model to a selected group of clients.
  2. Each client trains that model locally on its own data.
  3. Each client sends its updated model back — not its data.
  4. Server combines all the updates into a new global model.
  5. Repeat.
A subtlety worth sitting with The server never needs the raw data at any point in this loop. It only ever sees model weights. That's the entire privacy pitch of federated learning — though as I found out reading the follow-up paper on this same setup, "the server only sees weights" and "the server can't learn anything about the data" turn out to be two different claims. More on that in a separate post.
03 · The Constraint That Shapes Everything

Why communication, not computation, is the enemy here

In a data center, communication between machines is cheap and computation is the expensive part — which is why so much deep learning research is about faster GPUs. Federated learning inverts this completely.

Phones are frequently offline, on slow Wi-Fi, on metered mobile data, or simply asleep. Sending a neural network's worth of parameters back and forth — even a small one has hundreds of thousands of numbers — again and again is genuinely expensive. Meanwhile, modern phones have real processors sitting mostly idle. So the paper's whole strategy can be summarized in one sentence:

The core trade the paper makes Spend more computation on the client, in exchange for needing far fewer rounds of communication with the server.

The naive baseline: FedSGD

Before getting to FedAvg, it's worth seeing the boring version first. In FederatedSGD (FedSGD), each client computes a single gradient on its local data and immediately sends that gradient back. The server averages the gradients and takes one step. Then it all repeats.

\[ w_{t+1} \leftarrow w_t - \eta \sum_{k=1}^{K} \frac{n_k}{n} g_k \]

This works, but it means one communication round buys you exactly one gradient step. To train anything real, you need thousands of rounds — and every one of those rounds costs a slow, unreliable network trip.

04 · The Actual Algorithm

FedAvg: let clients train more before they talk to the server

The question the authors ask is almost embarrassingly simple: why should a phone communicate after just one gradient step? Let it train for a while first.

The numeric example that made this click for me

Numeric walkthrough Say the global model is a single number for simplicity: W = 100, sent to three phones.

Each phone trains locally on its own data:
Phone A → 90   Phone B → 95   Phone C → 100

Server averages: (90 + 95 + 100) / 3 = 95. That becomes the new global model, sent back out, and the whole thing repeats — maybe next time landing at 93.67, and so on. No phone ever revealed its data, only the number it arrived at after training.

A real network obviously has millions of numbers instead of one, but the averaging idea is exactly this, applied per-parameter.

The three knobs that control everything

ParameterMeaningEffect of increasing it
CFraction of clients selected per roundMore parallelism per round
ELocal epochs each client trains before sending backMore local computation, fewer rounds needed — up to a point
BLocal minibatch sizeSmaller B means more local updates per epoch
The tidy way to see it Setting E = 1 and B = ∞ (the whole local dataset as one batch) collapses FedAvg exactly back into FedSGD. FedAvg isn't a different algorithm bolted on top — it's the same family, with a dial for "how much do we compute locally before we talk to the server."

The math, written properly

The global objective decomposes into a weighted sum over clients:

\[ f(w) = \sum_{k=1}^{K} \frac{n_k}{n} F_k(w), \qquad F_k(w) = \frac{1}{n_k}\sum_{i \in P_k} f_i(w) \]

Each round, a client runs local SGD for E epochs starting from the shared global weights, then the server aggregates:

\[ w_{t+1} = \sum_{k \in S_t} \frac{n_k}{n_t} \, w_{t+1}^{k} \]
05 · The Part That Shouldn't Work, But Does

Averaging two neural networks sounds like it should produce garbage

Neural networks are non-convex. Naively, averaging the parameters of two different trained models — a fundamentally arbitrary operation in a huge, bumpy loss landscape — sounds like it should land you somewhere terrible.

The paper actually checks this. They trained two MNIST models on different small subsets of data, then plotted the loss along the line between them. Starting from two different random initializations, averaging is indeed bad — the midpoint has much higher loss than either parent model. But starting both models from the same initialization, averaging is not just safe, it's better than either parent alone.

Why this matters for FedAvg specifically Every round of FedAvg starts every client from the exact same shared global weights. That shared starting point is precisely the condition under which averaging works well — it's not a lucky coincidence, it's why the algorithm is designed this way.
06 · What Actually Makes This Hard

Non-IID and unbalanced data

A data-center cluster usually gets to assume every worker sees roughly the same kind of data. Real phones break that assumption completely, and the paper treats this as a defining property of the setting, not an edge case to footnote.

  • Non-IID — one user mostly types in Hindi, another mostly in English. Each client's local data distribution looks nothing like the global distribution.
  • Unbalanced — one user has generated 10 examples, another 10,000.
  • Massively distributed — there can be far more clients than examples per client.
  • Limited communication — offline, slow, or metered connections are the norm, not the exception.

To stress-test this, the paper's harshest experiment sorts MNIST by digit label and gives each client only 2 out of 10 digit classes. Most clients only ever see two digits. It's a deliberately pathological setup, designed to see exactly how far the algorithm can be pushed before it breaks.

07 · From Paper To Actual Code

What I built: a FedAvg reproduction on MNIST

I implemented the client/server loop from scratch in PyTorch — no federated learning library — and reproduced the paper's core question: does giving clients more local epochs (E) actually cut down the number of communication rounds needed?

Client drift — the thing I had to actually understand, not just report With only 2 digit classes per client, 20 local epochs is enough for each client to overfit hard to its narrow slice of data before sending weights back. Different clients drift toward wildly different local optima. When the server averages clients that disagree this strongly, the global model can temporarily get worse before recovering on the next round. This isn't a bug in my code — it's exactly the failure mode that later work like SCAFFOLD was built to correct with control variates.

I also ran the CNN under the same non-IID setup (E ∈ {1, 5}, 25 rounds) and saw the same story hold up: the CNN outperformed the 2NN outright, and E=5 beat E=1, which told me this wasn't an artifact of one particular architecture.

08 · For When You Just Need The Short Version

The cheat sheet

  • Federated Learning trains a shared model across many devices without ever centralizing their data.
  • FedSGD is the naive baseline — one gradient step per client, per communication round.
  • FedAvg lets each client run multiple local epochs before the server averages the resulting models, trading local computation for far fewer communication rounds.
  • C, E, B are the three knobs — client fraction, local epochs, local batch size.
  • Non-IID and unbalanced data are the defining, unavoidable difficulty of this setting, not an edge case.
  • Shared initialization is why naive parameter averaging works at all — start every client from the same weights each round, and averaging becomes safe.
  • Too much local computation isn't free: pushed too far on very skewed data, it causes client drift, visible as oscillating accuracy round to round.
