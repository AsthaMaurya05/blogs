Field Notes · Retrieval

RAG & Agentic RAG

An LLM only knows what's in its weights. Connecting it to the world outside them is the whole problem RAG exists to solve — and the whole reason a fixed pipeline eventually needs an agent in the loop.

01 — The Problem

Why RAG exists

A language model's knowledge is frozen at training time and limited to what fit inside its weights. Most real questions need something outside that: your documents, your database, today's news. Connecting an LLM to external data is the central need RAG solves.

Building the index

Before you can retrieve anything, your documents need to be turned into something searchable:

Documents→ Chunks→ Embedding Model→ Vectors→ Vector DB

Answering a question

At query time, the question is embedded and matched against the index via semantic search. Whatever comes back is injected into the prompt as context, and the model answers from that — not from memory.

Question→ Semantic Search→ Context Injection→ LLM→ Answer
context_window = input_prompt + chunks_from_vector_db The model never sees the whole document — only the pieces the search step decided were relevant.

02 — The Framework

Indexing, Retrieval, Generation

Every RAG system, however elaborate, breaks down into the same three stages:

Indexing

Taking your documents and processing them in some way so they can be easily retrieved later — chunking, embedding, and storing.

Retrieval

Given a question, pulling the document (or chunks) that are actually relevant to it out of the index.

Generation

Feeding the retrieved context alongside the original question into the LLM to produce the final answer.

03 — Before You Retrieve

Handling the query itself

A raw user question is rarely the best possible search query, and "the vector DB" is rarely the only place worth looking. Three things typically happen before retrieval ever fires:

Query Translation

Taking the question from the user and modifying it in some way to make it better suited for retrieval from the index — rephrasing, expanding, or breaking it into sub-questions.

Routing

Deciding which source should even answer this question, in one of two ways:

  • Logical routing — let the LLM itself choose the data source based on the question.
  • Semantic routing — embed the question and pick a route by similarity to the closest matching source or prompt.

Query Construction

Taking natural language and converting it into the DSL that whatever data source you're using actually needs:

Relational DB→Text-to-SQL
Graph DB→Text-to-Cypher
Vector DB→Self-Query Retriever
Put together: Question → Query Translation → Query Construction → Routing to the right store (graph DB, relational DB, or vector store) → the matching document comes back → Retrieval → Generation → Answer. Plain RAG runs this once, start to finish, with no judgment calls along the way.

04 — Where the Pipeline Runs Out of Road

Agentic RAG

A plain RAG pipeline always retrieves once and always generates once — whether or not retrieval was actually needed, and whether or not what came back was any good. Agentic RAG replaces those fixed steps with an agent that makes a decision at each one: whether to look something up, where to look, and whether the answer it produced is actually good enough to return.

The agentic RAG loop — every arrow here is a decision, not a fixed step.

Walking through the loop

  • An agent first rewrites the initial query — sharpening it the same way query translation does in plain RAG, but as a live decision rather than a fixed rule.
  • A second agent call asks "do I need more details?" If not, it skips retrieval entirely and goes straight to generation — plain RAG never has this option, it always retrieves.
  • If more is needed, another agent call decides which source will actually help: the vector DB, an external tool or API, or the open internet.
  • Whatever comes back — retrieved context plus the updated query — is handed to the LLM to generate a response.
  • Before returning anything, one more agent call checks: is the answer actually relevant? If yes, that's the final response. If no, the loop doesn't just fail — it goes back to rewriting the query and tries again.
The difference in one line: plain RAG is a pipeline; agentic RAG is a loop with judgment calls. Retrieval becomes something the model decides to do, not something that always happens — and a bad answer becomes a reason to retry, not a final answer.
